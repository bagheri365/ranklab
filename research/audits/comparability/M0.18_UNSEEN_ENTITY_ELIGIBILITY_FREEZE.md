# M0.18 — Unseen-Entity Scoring Eligibility Freeze

## Status

**M0.15 shared evaluation support: FROZEN**

**Training-index scoring eligibility: FROZEN**

**Cold-start fallback scoring: NOT USED**

**Rule applies to Popularity, BPR, LightGCN: YES**

**Post-eligibility candidate audit: FROZEN BEFORE EXECUTION**

**M1: BLOCKED**

M0.18 freezes how RankLab handles evaluation users/items that were not present
in the frozen BPR/LightGCN training index universe.

## 1. Evidence from M0.17

On primary shared-user/shared-item support:

### Standard

- users: 25,877;
- training-seen users: 22,882;
- unseen users: 2,995;
- seen-user fraction: 88.4260%;
- items: 6,618;
- training-seen items: 6,598;
- unseen items: 20;
- fully scoreable candidate-pair fraction: 92.1067%.

### Randomized

- users: 25,877;
- training-seen users: 22,882;
- unseen users: 2,995;
- items: 6,618;
- training-seen items: 6,598;
- unseen items: 20;
- fully scoreable candidate-pair fraction: 91.2899%.

The coverage gap is therefore driven primarily by users, not items.

## 2. Frozen rule

After applying the M0.15 regime-support restriction, an evaluation row is
eligible for scoring only when:

- `user_id` belongs to the frozen pairwise-eligible training user index; and
- `video_id` belongs to the frozen training item index.

This rule is applied identically to:

- Popularity;
- BPR;
- LightGCN.

## 3. Why not invent cold-start embeddings

BPR and LightGCN were not trained with a frozen cold-start mechanism.

Assigning a zero vector, random vector, global-average score, or some other
fallback after observing evaluation coverage would introduce a new model
component after model selection.

RankLab therefore does not invent a post-hoc cold-start representation.

## 4. Why Popularity is restricted too

Popularity technically can ignore user identity and score an unseen item as
zero.

However, allowing Popularity to evaluate users or items that BPR/LightGCN
cannot score would give the baseline a different evaluation population.

The study's model-ordering question requires all compared models to operate on
the same candidate population.

Therefore the training-index eligibility restriction is global.

## 5. Pair intersection remains unnecessary

M0.18 does not require a user-item pair to have appeared in training.

It requires only that the user and item were individually indexed during
training.

It also does not require the evaluation pair to appear in both logging regimes.

Thus RankLab still preserves regime-specific exposure pairs.

## 6. Consequence for candidate-structure decisions

The M0.16 candidate audit occurred before this training-index restriction.

Because M0.18 removes 2,995 primary-support users and a small number of items,
the exact candidate-depth and zero-relevance counts must be re-measured before
freezing:

- minimum candidate set size;
- less-than-K behavior;
- zero-relevance handling.

M0.18 therefore includes a label-only post-eligibility candidate audit.

## 7. Audit guardrail

The post-eligibility audit:

- loads no checkpoint;
- computes no model score;
- computes no model ranking;
- computes no ranking metric.

It only reports candidate and target-relevance structure after all currently
frozen support/eligibility filters.

