# M0.9d — LightGCN Hyperparameter Sweep Protocol

## Status

**LightGCN optimization-scale audit: COMPLETED**

**LightGCN hyperparameter-search protocol: FROZEN BEFORE SWEEP EXECUTION**

**LightGCN tuning-seed configuration: NOT YET SELECTED**

**Primary multi-seed LightGCN checkpoints: NOT YET FIT**

**Overall M0 protocol: UNFROZEN**

This document freezes the LightGCN model-selection search before any configuration in the formal sweep is executed.

It follows the same chronology principle used for BPR:

1. implement and test the numerical model;
2. establish a deterministic real-data pipeline;
3. diagnose learning capability;
4. for LightGCN only, run a predeclared optimization-scale audit;
5. freeze the formal search protocol;
6. only then execute the search.

---

## 1. Evidence used to define the learning-rate range

The predeclared M0.9c audit varied only learning rate over:

- `0.1`
- `0.5`
- `1.0`
- `2.0`
- `5.0`

All other settings were fixed.

Observed behavior was qualitatively:

- `0.1`: validation ranking unchanged across five epochs;
- `0.5`: validation ranking unchanged across five epochs;
- `1.0`: validation ranking began to move in later epochs;
- `2.0`: validation ranking changed immediately after epoch 1 while remaining numerically stable;
- `5.0`: numerically stable, but validation was already below the lower-rate region at epoch 1 and remained lower.

The audit was **not** used to declare a winning learning rate.

Its role was only to bound the formal search.

Therefore the formal LightGCN learning-rate grid is:

- `0.5`
- `1.0`
- `2.0`

Rationale:

- `0.5` anchors the upper edge of the nearly ranking-static region;
- `1.0` captures the transition where rankings begin to change;
- `2.0` provides a stronger but still stable update scale;
- `0.1` is omitted because it adds little information relative to `0.5` over the audit horizon;
- `5.0` is omitted because the audit already showed it moving beyond the more useful lower-rate region.

No new learning rates may be added after the formal sweep is observed.

## 2. Formal search grid

The LightGCN sweep contains exactly 27 configurations.

### Embedding dimension

- `16`
- `32`
- `64`

This mirrors the BPR capacity grid and allows a controlled comparison of embedding capacity.

### Propagation depth

- `1`
- `2`
- `3`

Propagation depth is LightGCN-specific and therefore must be searched rather than inherited from BPR.

The range is intentionally shallow because RankLab is testing LightGCN as a controlled collaborative-filtering baseline, not conducting an unrestricted architecture search.

### Learning rate

- `0.5`
- `1.0`
- `2.0`

These values come from the frozen M0.9c optimization-scale audit.

### Regularization

Fixed at:

- `1e-4`

Regularization is **not** treated as a search axis in this LightGCN protocol.

This is deliberate.

A full Cartesian search over three embedding dimensions, three propagation depths, three learning rates, and three regularization values would require 81 full-graph configurations.

RankLab instead spends the 27-configuration budget on the three axes most central to the comparison:

- representation capacity;
- graph propagation depth;
- model-specific optimization scale.

The resulting limitation must be reported honestly:

> LightGCN regularization was fixed at `1e-4`; it was not independently optimized.

This differs from the BPR search, where regularization was an explicit search axis.

That asymmetry should be retained in the final methodology rationale.

## 3. Fixed training settings

For every configuration:

- epochs: `30`
- gradient chunk size: `8192`
- initialization std: `0.01`
- tuning seed: `0`
- validation K: `10`
- positive target: `is_click`
- training dates: Apr 9–16
- validation dates: Apr 17–21
- negative sampling: frozen same-user logged-negative rule
- graph population: pairwise-eligible positive users only

All 30 epochs are executed.

There is no early stopping.

---

## 4. Within-configuration epoch selection

For each configuration:

1. compute validation macro NDCG@10 after every epoch;
2. choose the strict maximum validation value;
3. if multiple epochs have exactly equal validation values, select the earliest epoch.

The full 30-epoch run is still completed even if the best epoch occurs early.

---

## 5. Between-configuration selection

The selected tuning-seed configuration is the configuration with the strict maximum best validation macro NDCG@10.

No post-hoc tolerance is introduced.

If two configurations have exactly equal best validation values, the frozen tie-break is:

1. fewer propagation layers;
2. lower embedding dimension;
3. lower learning rate;
4. earlier selected epoch.

This favors the simpler graph architecture under a true numerical tie.

---

## 6. Seed policy

Hyperparameter tuning uses only:

- seed `0`

This matches the BPR tuning procedure.

The formal multi-seed primary LightGCN checkpoint set is **not** part of this sweep.

After the tuning-seed configuration is selected and documented, the primary seed set must be frozen separately before fitting the final evaluation checkpoints.

---

## 7. Search guardrails

The following are prohibited after sweep execution begins:

- adding new embedding dimensions;
- adding new propagation depths;
- adding new learning rates;
- changing regularization;
- changing epoch budget;
- changing the selection metric;
- adding a validation tolerance after observing near-ties;
- inspecting Apr 22–May 8 labels to resolve a tuning decision;
- inspecting randomized-policy evaluation labels to resolve a tuning decision.

If the selected configurations are separated by a tiny numerical margin, RankLab will report that fact rather than reopening the grid.

---

## 8. Why the LightGCN search is not identical to BPR

A controlled comparison does not require every model to have the same hyperparameter names.

It requires the training/evaluation protocol to be controlled while allowing model-specific parameters to be handled transparently.

BPR searched:

- embedding dimension;
- learning rate;
- regularization.

LightGCN searches:

- embedding dimension;
- propagation depth;
- learning rate;

with regularization fixed.

The extra LightGCN optimization-scale audit was necessary because the M0.9b real-data behavior showed that the BPR learning-rate scale did not transfer directly to the full-graph LightGCN optimizer.

This difference is part of the research process and should remain visible in the later BPR-vs-LightGCN rationale.

---

## 9. What this sweep may select

The sweep may select:

- one LightGCN tuning-seed configuration;
- one best tuning-seed epoch for that configuration;
- one corresponding tuning-seed checkpoint.

It does **not** freeze:

- the primary multi-seed LightGCN checkpoint set;
- seed aggregation rules;
- M1 evaluation support restrictions;
- M1 statistical inference;
- the overall RankLab protocol.
