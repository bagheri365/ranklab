# M0.16 — Candidate-Structure Audit Protocol

## Status

**M0.15 support policy: FROZEN**

**Candidate-structure audit design: FROZEN BEFORE EXECUTION**

**Model checkpoints/scores used by audit: NO**

**Minimum candidate-set size: UNFROZEN**

**Less-than-K rule: UNFROZEN**

**Zero-relevance-user rule: UNFROZEN**

**M1: BLOCKED**

This milestone freezes a descriptive evaluation-label audit before RankLab
decides the remaining candidate/metric edge cases.

The audit intentionally does not load or score Popularity, BPR, or LightGCN.

## 1. Purpose

The next protocol decisions affect which users contribute to macro NDCG and how
small candidate sets are interpreted.

Rather than choose those rules without knowing their population consequences,
RankLab first measures candidate structure under the already-frozen support
policy.

Because no model scores are observed, this audit cannot be used to choose edge
rules that favor a model.

## 2. Support variants audited

The audit reports all three predeclared M0.15 supports:

1. primary shared users + shared videos;
2. shared users + shared videos + shared tabs;
3. shared users + shared videos + `tab=1`.

Both standard and randomized evaluation are reported separately.

## 3. Provisional pair collapse used only for structural counting

Repeated retained exposure rows for the same `(user_id, video_id)` are
collapsed to one structural candidate.

For each target independently, structural relevance is:

> 1 if any retained row for the pair has target value 1; otherwise 0.

This lets the audit count candidate and relevance structure.

M0.16 does not yet promote that rule to the final M1 evaluator; that freeze
comes after the audit.

## 4. Quantities reported

For each regime/support combination:

- retained exposure rows;
- unique user-video candidate pairs;
- number of duplicate exposure rows removed by pair collapse;
- users;
- candidate count minimum;
- candidate count mean;
- candidate count median;
- candidate count p90;
- candidate count maximum;
- users with at least 2 candidates;
- users with at least 10 candidates.

For each target (`is_click`, `long_view`):

- users with at least one relevant candidate;
- zero-relevance users;
- relevant users with at least 2 candidates;
- relevant users with at least 10 candidates;
- relevant candidate pairs;
- candidate-pair relevance prevalence.

## 5. Guardrail

The audit must not:

- load a recommender checkpoint;
- fit a new recommender;
- score candidates;
- rank candidates;
- compute NDCG;
- compare model performance.

The resulting counts may inform population/edge-case semantics but not model
selection.

## 6. Execution

After this code and protocol note are committed, run:

```bash
python -m ranklab.evaluation.candidate_audit_cli \
  --data-dir data/raw/KuaiRand-Pure/data \
  --output runs/m0/candidate_structure_audit.json
```

The resulting JSON remains a generated run artifact.

## 7. Decisions that remain open until after execution

M0.16 does not freeze:

- final duplicate-collapse rule;
- final target relevance rule;
- minimum candidate-set size;
- behavior when candidate count is below K;
- zero-relevance-user handling;
- final primary K/metric registry fields;
- seed aggregation;
- statistical inference.

Those will be frozen in the next milestone without observing recommender
metrics.
