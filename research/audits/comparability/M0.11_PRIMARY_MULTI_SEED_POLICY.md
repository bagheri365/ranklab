# M0.11 — Shared Primary Multi-Seed Fitting Policy

## Status

**BPR tuning-seed configuration: FROZEN**

**LightGCN tuning-seed configuration: FROZEN**

**Primary seed set: FROZEN BEFORE FINAL FITTING**

**Primary per-model epoch counts: FROZEN BEFORE FINAL FITTING**

**Primary multi-seed checkpoints: NOT YET FIT**

**Overall M0 protocol: UNFROZEN**

This document freezes the shared multi-seed fitting policy for the selected BPR and LightGCN configurations before any primary multi-seed checkpoints are trained.

The purpose is to prevent final fitting from quietly becoming a second round of validation tuning.

---

## 1. Shared primary seed set

The primary seed set is:

- `0`
- `1`
- `2`
- `3`
- `4`

Exactly five seeds are used for both BPR and LightGCN.

No additional seeds may be added after primary fitting results are observed unless a later protocol amendment explicitly reopens this decision before M1.

Using the same seed IDs for both models simplifies paired seed-level diagnostics while keeping the model-specific randomness separate.

---

## 2. No per-seed hyperparameter re-tuning

For each model, every primary seed uses the already frozen tuning-seed configuration.

### BPR fixed configuration

- embedding dimension: `32`
- learning rate: `0.05`
- regularization: `1e-3`
- batch size: `4096`
- initialization std: `0.01`

### LightGCN fixed configuration

- embedding dimension: `32`
- propagation layers: `2`
- learning rate: `2.0`
- regularization: `1e-4`
- gradient chunk size: `8192`
- initialization std: `0.01`

No seed may use a different configuration because its validation result looks better.

---

## 3. No per-seed epoch re-selection

Primary fitting does **not** re-run validation-based epoch selection for every seed.

Instead, the epoch counts selected during tuning are reused as fixed training budgets.

### BPR

Fixed primary epoch count:

`1`

### LightGCN

Fixed primary epoch count:

`28`

Reason:

The tuning stage already used Apr 17–21 validation to choose the model configuration and selected epoch.

If every primary seed were allowed to choose its own best validation epoch, validation would be reused again to optimize each final seed-specific checkpoint.

That would turn the final fit into another tuning procedure.

Therefore primary seeds train for the fixed selected number of epochs and save the checkpoint at that fixed endpoint.

---

## 4. Why seed 0 is included

Seed `0` is retained in the five-seed primary set.

It was also used during hyperparameter tuning.

This means the seed-0 primary checkpoint is not an independent replicate of model selection.

However, the project is not using the five seeds to estimate an unbiased hyperparameter-selection distribution.

The seeds are used to characterize stochastic variation of the already frozen model specification.

The tuning history of seed 0 must remain disclosed.

If later inferential procedures require strict separation between tuning and evaluation randomness, that must be handled explicitly in the statistical protocol rather than silently dropping or replacing seed 0 after seeing results.

---

## 5. Checkpoint naming

Primary checkpoints use deterministic names.

### BPR

- `bpr_seed0.npz`
- `bpr_seed1.npz`
- `bpr_seed2.npz`
- `bpr_seed3.npz`
- `bpr_seed4.npz`

### LightGCN

- `lightgcn_seed0.npz`
- `lightgcn_seed1.npz`
- `lightgcn_seed2.npz`
- `lightgcn_seed3.npz`
- `lightgcn_seed4.npz`

Each checkpoint must have a SHA256 recorded in a model-specific primary-fit manifest.

---

## 6. Required manifest fields

For every primary checkpoint, record at minimum:

- model name;
- seed;
- data SHA256;
- frozen protocol SHA256;
- selected hyperparameters;
- fixed epoch count;
- training-pair counts;
- indexed user count;
- indexed item count;
- checkpoint filename;
- checkpoint SHA256.

The manifest should also record that:

- no per-seed validation selection occurred;
- no Apr 22–May 8 evaluation labels were used;
- no randomized-policy evaluation labels were used.

---

## 7. Reproducibility

At least one non-tuning primary seed for each model should be repeated before M1.

Recommended repeat:

- BPR seed `1`;
- LightGCN seed `1`.

The repeated checkpoint SHA256 must match the original seed-1 checkpoint SHA256.

This verifies that deterministic execution generalizes beyond tuning seed 0.

---

## 8. How seed-level results will be used later

This decision freezes fitting only.

It does **not** yet freeze how M1 performance will be aggregated across seeds.

Potential later choices include:

- reporting all seed-level metrics;
- arithmetic mean across seeds;
- median across seeds;
- paired model contrasts by seed;
- bootstrap procedures that account for users and seeds separately.

Those decisions belong to the later evaluation/statistical protocol.

They must not be back-propagated into model fitting.

---

## 9. Why the policy is shared across models

The BPR and LightGCN tuning procedures differed in model-specific ways.

But the final seed policy should be shared wherever possible.

Both models therefore use:

- the same five seed IDs;
- fixed already-selected hyperparameters;
- fixed already-selected epoch count;
- no per-seed validation re-selection;
- deterministic checkpoint naming;
- SHA256 verification;
- at least one repeated non-tuning seed.

This creates a cleaner comparison at the final fitting stage.

---

## 10. What this decision freezes

Frozen:

- primary seeds: `0,1,2,3,4`;
- BPR primary epochs: `1`;
- LightGCN primary epochs: `28`;
- no per-seed hyperparameter tuning;
- no per-seed epoch re-selection;
- deterministic checkpoint naming;
- required checkpoint hashing;
- repeatability check on a non-tuning seed.

---

## 11. What remains open

Not yet frozen:

- primary checkpoint bytes;
- seed aggregation rules;
- final support restrictions;
- final evaluation implementation;
- statistical inference;
- confidence intervals;
- M1 execution;
- overall RankLab protocol.

---

## 12. Decision summary

RankLab will fit exactly five primary checkpoints per selected model using seeds:

`0,1,2,3,4`.

BPR uses its frozen selected configuration for exactly:

`1 epoch`.

LightGCN uses its frozen selected configuration for exactly:

`28 epochs`.

No primary seed is allowed to re-select hyperparameters or its own validation-best epoch.

This preserves the distinction between:

- model selection;
- final stochastic fitting;
- later evaluation.
