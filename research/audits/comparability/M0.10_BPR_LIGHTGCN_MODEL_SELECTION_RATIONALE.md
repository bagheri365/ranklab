# M0.10 — BPR and LightGCN Model-Selection Rationale

## Status

**BPR tuning-seed configuration: SELECTED AND FROZEN**

**LightGCN tuning-seed configuration: SELECTED AND FROZEN**

**Joint model-selection rationale: RECORDED**

**Primary multi-seed checkpoint sets: NOT YET FROZEN**

**Overall M0 protocol: UNFROZEN**

This document records the chronology and rationale that produced the selected BPR and LightGCN tuning-seed configurations.

Its purpose is methodological transparency.

It explains not only what was selected, but why the two model-development paths were similar in some places and intentionally different in others.

The goal is to preserve the research process before primary multi-seed fitting and before M1 evaluation begins.

---

## 1. Shared scientific objective

BPR and LightGCN are not being tuned as unrelated standalone systems.

They are two controlled recommender baselines that will later be evaluated under the same RankLab question:

> Is offline model selection stable when the same trained recommenders are evaluated across different exposure regimes and behavioral targets?

For that reason, the project tries to hold the training and validation protocol constant wherever doing so is scientifically meaningful.

The model-specific parts are allowed to differ, but those differences must be explicit and frozen before evaluation.

---

## 2. Shared frozen training contract

Both BPR and LightGCN use the same training contract.

### Data source

Only standard-policy history is used for training and validation.

### Training dates

Apr 9–16, 2022.

### Validation dates

Apr 17–21, 2022.

### Primary training signal

`is_click`.

The project originally preferred a training target distinct from the later evaluation targets, but the candidate engagement signals were too sparse in validation.

That preference was therefore revised before model fitting.

The same checkpoints will later be evaluated under both:

- `is_click`;
- `long_view`.

### Positive pair definition

A user-video pair is positive if there is any click for that pair in the training slice.

Pairs are collapsed so repeated exposure does not create repeated positive edges.

### Eligible logged negative

A user-video pair is an eligible negative if:

- the user was exposed to the item in the training slice;
- the pair has no click anywhere in the training slice.

### Pairwise user eligibility

A user is pairwise-eligible only if the user has:

- at least one positive pair;
- at least one eligible logged negative pair.

### Negative sampling

For each positive pair and each epoch:

- sample one negative from the same user's eligible logged negatives;
- sample uniformly;
- sample with replacement;
- resample each epoch;
- use the model seed for deterministic reproducibility.

### Validation

The validation ranking unit is one user.

Candidate items are unique logged user-video pairs in Apr 17–21.

Relevance is binary any-click.

The primary validation metric is:

macro NDCG@10.

This validation setup is intentionally shared across BPR and LightGCN.

## 3. Why BPR was implemented first

BPR was implemented before LightGCN because it provides the simpler pairwise collaborative-filtering baseline.

That sequencing served several purposes:

1. validate the frozen pair construction;
2. validate same-user logged-negative sampling;
3. validate deterministic indexing and checkpointing;
4. validate the macro logged-candidate NDCG implementation;
5. observe the behavior of the frozen validation protocol on a simpler latent-factor model before adding graph propagation.

This meant that several later LightGCN components could inherit already-tested infrastructure rather than reopening protocol decisions.

BPR therefore served both as a baseline model and as the first end-to-end validation of the pairwise training contract.

---

## 4. BPR implementation path

The BPR path proceeded in four main steps.

### 4.1 Deterministic numerical core

The BPR matrix-factorization core established:

- deterministic ID indexing;
- seeded Gaussian embedding initialization;
- user-item dot-product scoring;
- same-user logged-negative sampling;
- deterministic BPR SGD;
- checkpoint save/load without pickle;
- checkpoint round-trip reproducibility.

This separated the numerical model from real-data plumbing.

### 4.2 Frozen-contract real-data pipeline

The BPR pipeline then applied the frozen KuaiRand contract.

The real-data run reproduced the previously audited training counts, including:

- 1,011,214 training rows;
- 463,260 positive pairs;
- 504,572 negative-only pairs;
- 23,638 pairwise-eligible users;
- 1,206 positive users excluded because they had no eligible logged negative;
- 458,854 pairwise-eligible positive pairs;
- 7,527 indexed items.

The pipeline selected the best validation epoch using strict macro NDCG@10 with earliest epoch on an exact tie.

Repeated execution with the same seed produced an identical checkpoint SHA256 and identical manifest.

### 4.3 BPR learning diagnostic

The initial full-data BPR smoke run showed very small changes in aggregate loss.

Rather than assuming a bug or assuming the optimizer was learning, RankLab ran a stronger real-data diagnostic on a 500-user subset.

That diagnostic demonstrated that the implementation could reduce fixed-triplet BPR loss.

This established:

> the BPR implementation can learn, while the aggregate full-data training curve is nearly flat under the selected optimization scale.

This diagnostic was not used for hyperparameter selection.

### 4.4 BPR formal sweep

Before observing sweep results, RankLab froze a 27-configuration BPR grid:

- embedding dimension: 16, 32, 64;
- learning rate: 0.01, 0.05, 0.1;
- regularization: `1e-5`, `1e-4`, `1e-3`.

Fixed:

- batch size: 4096;
- epochs: 30;
- initialization std: 0.01;
- tuning seed: 0;
- validation metric: macro NDCG@10.

No early stopping was used.

No adaptive grid expansion was allowed.

The strict numerical winner was:

- embedding dimension: 32;
- learning rate: 0.05;
- regularization: `1e-3`;
- selected epoch: 1;
- validation macro NDCG@10: `0.7659499845152606`;
- checkpoint SHA256:
  `45360222adaf4f640de8cc1e459f27bcb72fd4685adae210aace69870c585997`.

The winning margin over nearby 32-dimensional configurations was extremely small.

Therefore the project froze the strict numerical winner but explicitly refused to claim meaningful practical superiority of its exact regularization value.

## 5. What BPR taught us before LightGCN

The BPR path established several lessons that were carried forward.

### 5.1 Determinism must be physically verified

RankLab did not rely only on deterministic-looking code.

It repeated real runs and compared:

- checkpoint SHA256;
- manifests.

The same standard was therefore applied to LightGCN.

### 5.2 Near-flat loss does not by itself prove an implementation bug

The BPR diagnostic showed that a model can demonstrably learn even when the aggregate full-data loss moves only slightly.

This became important when LightGCN later showed similarly small aggregate loss movement.

### 5.3 Tiny validation differences must be reported as tiny

The BPR winner was selected by a predeclared strict-maximum rule.

Because the margin was extremely small, RankLab did not retrofit a tolerance or reopen the grid.

This same interpretation rule was later applied to LightGCN.

### 5.4 Validation NDCG is logged-candidate ranking, not full-catalog retrieval

The frozen validation candidate depth is shallow:

- median approximately 4;
- p90 approximately 12.

Therefore an NDCG around 0.766 is not evidence of full-catalog retrieval performance.

This caveat applies equally to both models.

---

## 6. Why LightGCN could not simply reuse the BPR implementation path

LightGCN inherits the pairwise training contract but introduces a graph propagation mechanism.

Its mathematical semantics differ from BPR in important ways:

- positive click pairs form a bipartite graph;
- propagation uses symmetric degree normalization;
- there are no feature transformations;
- there are no nonlinear activations;
- final embeddings average layer 0 through layer L;
- BPR loss is computed on propagated embeddings;
- gradients must flow back through graph propagation to the base embeddings.

Therefore LightGCN required a separately tested numerical core rather than wrapping the BPR model in a graph-like interface.

---

## 7. LightGCN graph-population decision

A model-specific comparability choice was required.

Some positive users have no eligible same-user logged negative.

BPR must exclude those users from pairwise training.

LightGCN could, in principle, retain their positive interactions as graph-only context even though they cannot contribute a BPR triplet.

RankLab deliberately did not do this.

Instead:

> LightGCN excludes those users from both the graph and the pairwise loss.

Reason:

Allowing graph-only users would give LightGCN access to an additional training population that BPR cannot use.

For this controlled comparison, population alignment was preferred over extracting extra graph signal.

This is a model-specific design choice and should be reported as such.

---

## 8. LightGCN implementation path

### 8.1 Deterministic numerical core

The LightGCN core established and tested:

- pair-collapsed positive graph edges;
- symmetric degree normalization;
- deterministic initialization;
- propagation without transforms or nonlinearities;
- averaging of layer 0 through layer L;
- BPR loss on propagated embeddings;
- back-propagation through the linear graph operator;
- checkpoint round-trip reproducibility.

A transparent full-batch implementation was used first so the numerical semantics could be tested independently of scale optimizations.

### 8.2 Memory-bounded real-data pipeline

For full KuaiRand training, RankLab retained the same mathematical full-batch gradient but accumulated triplet gradients in chunks.

The procedure is:

1. propagate embeddings once from the epoch-start base embeddings;
2. accumulate triplet gradients in deterministic chunks;
3. back-propagate the accumulated gradient through graph propagation;
4. apply one base-embedding update.

The chunk size is treated as an engineering parameter rather than a model-selection axis.

This preserved the tested M0.9a semantics while reducing peak memory use.

### 8.3 Real-data reproducibility

The first real LightGCN smoke run reproduced the frozen pairwise population:

- 23,638 indexed users;
- 458,854 eligible positive pairs;
- 458,854 graph edges;
- 7,527 indexed items.

Repeating the run with the same seed produced:

- identical manifests;
- identical checkpoint SHA256.

This established deterministic full-data execution.

### 8.4 LightGCN learning diagnostic

The initial LightGCN smoke run at learning rate 0.1 produced almost no visible validation movement.

A separate 500-user real-data diagnostic then used a stronger learning rate and demonstrated a reduction in fixed-triplet BPR loss.

The decrease was small but positive.

Therefore RankLab concluded:

> the LightGCN implementation can learn, but the effective update scale of the full-graph optimizer is substantially smaller than the mini-batch BPR optimizer under comparable nominal learning rates.

This observation motivated one extra step that BPR did not need.

## 9. Why LightGCN required a pre-sweep optimization-scale audit

RankLab did not want to copy the BPR learning-rate grid mechanically.

The reason was empirical and model-specific:

- BPR used mini-batch SGD;
- LightGCN accumulated one full-batch graph-aware gradient per epoch;
- nominal learning rates therefore did not have directly comparable meanings.

Before the formal LightGCN sweep, RankLab froze and executed a narrow optimization-scale audit.

Only learning rate varied:

- 0.1;
- 0.5;
- 1.0;
- 2.0;
- 5.0.

Fixed:

- embedding dimension 32;
- one propagation layer;
- regularization `1e-4`;
- five epochs;
- seed 0.

The audit was explicitly not a model-selection sweep.

Its purpose was only to bound the formal learning-rate range.

Observed pattern:

- 0.1: validation unchanged across five epochs;
- 0.5: validation unchanged across five epochs;
- 1.0: validation began changing at later epochs;
- 2.0: validation changed immediately after epoch 1 while remaining numerically stable;
- 5.0: numerically stable but already below the lower-rate validation region.

Therefore the formal LightGCN sweep used:

- 0.5;
- 1.0;
- 2.0.

The audit did not declare 0.5, 1.0, or 2.0 a winner.

It only defined a defensible bounded search range.

---

## 10. Why the LightGCN sweep was not identical to BPR

BPR and LightGCN do not have the same model-specific hyperparameters.

A controlled comparison does not require identical hyperparameter names.

It requires:

- shared data;
- shared target;
- shared validation protocol;
- shared leakage guardrails;
- transparent model-specific tuning.

### BPR search axes

BPR searched:

- embedding dimension;
- learning rate;
- regularization.

### LightGCN search axes

LightGCN searched:

- embedding dimension;
- propagation depth;
- learning rate.

LightGCN regularization was fixed at:

`1e-4`.

This was predeclared.

Adding a three-level regularization axis would have expanded the LightGCN search from 27 to 81 full-graph runs.

RankLab instead allocated the 27-configuration budget to:

- representation capacity;
- graph propagation depth;
- model-specific optimization scale.

Therefore the correct reporting language is:

> BPR regularization was tuned, while LightGCN regularization was fixed at `1e-4`.

RankLab must not imply that LightGCN regularization was independently optimized.

## 11. LightGCN formal sweep

Before execution, RankLab froze exactly 27 configurations:

- embedding dimension: 16, 32, 64;
- propagation layers: 1, 2, 3;
- learning rate: 0.5, 1.0, 2.0.

Fixed:

- regularization: `1e-4`;
- gradient chunk size: 8192;
- epochs: 30;
- initialization std: 0.01;
- tuning seed: 0;
- validation metric: macro NDCG@10.

All configurations completed all 30 epochs.

No early stopping was used.

No adaptive grid expansion was allowed.

The strict numerical winner was:

- embedding dimension: 32;
- propagation layers: 2;
- learning rate: 2.0;
- regularization: `1e-4`;
- selected epoch: 28;
- validation macro NDCG@10: `0.76624771751633`;
- checkpoint SHA256:
  `50438670f62a938731eba465fef44302a3e5623572f2e3eb46f0d7824a7cc189`.

The selected checkpoint was physically verified as byte-identical to the winning configuration's best checkpoint.

Exactly 27 configuration manifests were verified.

## 12. What the LightGCN sweep actually established

The strongest LightGCN result is architectural rather than an exact learning-rate result.

### Embedding dimension

The 32-dimensional family was stronger than the 16- and 64-dimensional regions.

### Propagation depth

At 32 dimensions:

- two layers formed the strongest region;
- one layer was lower;
- three layers were also lower.

This is the clearest LightGCN-specific search signal.

### Learning rate

Within the strongest `d32_l2` family:

- LR 2.0: `0.76624771751633`;
- LR 0.5: `0.7662463559707516`;
- LR 1.0: `0.7662442257968052`.

The difference between LR 2.0 and LR 0.5 is approximately:

`1.36e-6`.

Therefore the strict frozen rule selects LR 2.0, but the project does not claim meaningful practical superiority of LR 2.0 over LR 0.5.

## 13. BPR epoch 1 versus LightGCN epoch 28

The selected BPR checkpoint occurs at epoch 1.

The selected LightGCN checkpoint occurs at epoch 28.

This difference is methodologically important.

### BPR

The validation trajectory was effectively near-flat from the beginning.

Later epochs did not improve on epoch 1 under the selected BPR configuration.

### LightGCN

The winning LightGCN trajectory is also near-flat in absolute magnitude, but small ranking changes continue throughout training.

For the winning configuration:

- epoch 23 is close to the maximum;
- epoch 27 is closer still;
- epochs 28 and 29 exactly tie at the maximum;
- epoch 30 decreases slightly.

The frozen earliest-tie rule therefore selects epoch 28.

This is not interpreted as evidence that LightGCN universally needs exactly 28 epochs.

The correct interpretation is:

> under this full-graph optimizer and this validation protocol, useful ranking movement emerged later than for BPR, and the strict numerical maximum occurred in a near-flat late-epoch region.

This behavior is consistent with the earlier optimization-scale audit.

## 14. Shared interpretation of near-flat losses

Both selected models train with aggregate pairwise losses close to `log(2)`.

This must be interpreted carefully.

The project separately demonstrated learning capability for each implementation using real-data diagnostics.

Therefore the full-data near-flat curves do not by themselves imply numerical failure.

More precise statements are:

- both implementations can learn;
- the full-data optimization scales produce relatively small aggregate changes;
- same-user negative resampling makes epoch losses non-monotone;
- validation candidate sets are shallow;
- strict ranking metrics can change from small score perturbations.

This caveat should remain visible in any final methods section.

---

## 15. Shared selection philosophy

Both model-selection paths use the same methodological philosophy.

### Predeclare before observing

Search spaces and selection rules are committed before sweep execution.

### Strict numerical maximum

The winner is the strict maximum validation macro NDCG@10.

### No post-hoc tolerance

If winners are separated by tiny margins, RankLab reports that fact.

It does not invent a tolerance after seeing results.

### No adaptive grid expansion

The grid is not expanded because the observed winner looks inconvenient or inconclusive.

### Tuning seed only

Hyperparameter selection uses seed 0.

Primary multi-seed fitting remains separate.

### Evaluation labels remain untouched

No Apr 22–May 8 standard-policy labels or randomized-policy evaluation labels are used to break tuning decisions.

---

## 16. Why the two paths are intentionally not perfectly symmetric

The project does not treat procedural symmetry as more important than model validity.

BPR and LightGCN share the same training/evaluation contract.

But model-specific engineering differs.

### BPR-specific

- mini-batch SGD;
- regularization included in the formal search;
- no pre-sweep LR audit required.

### LightGCN-specific

- positive interaction graph;
- symmetric normalized propagation;
- layer averaging;
- graph-population alignment decision;
- memory-bounded full-batch gradient accumulation;
- explicit propagation-depth search;
- pre-sweep optimization-scale audit;
- fixed regularization.

These differences are not protocol failures.

They are documented model-specific choices made before evaluation.

## 20. Final methodological takeaway

The BPR and LightGCN paths were deliberately controlled without being artificially identical.

They share:

- data;
- training target;
- dates;
- pair semantics;
- negative concept;
- validation candidates;
- validation metric;
- tuning seed;
- leakage guardrails;
- precommit-before-observation discipline.

They differ where the models genuinely require different treatment:

- BPR uses mini-batch latent-factor optimization;
- LightGCN uses graph propagation and full-graph gradient accumulation;
- LightGCN required an optimization-scale audit;
- LightGCN searches propagation depth;
- BPR searches regularization while LightGCN fixes it.

The selected tuning-seed models are numerically close on the shallow logged-candidate validation task.

The purpose of RankLab is not to declare a universal winner from this validation split.

The purpose is to freeze reasonable trained recommenders under a controlled development process, then test whether their apparent ordering remains stable when exposure regime and behavioral target change.

That downstream stability question remains open until the remaining M0 protocol decisions are frozen and M1 begins.
