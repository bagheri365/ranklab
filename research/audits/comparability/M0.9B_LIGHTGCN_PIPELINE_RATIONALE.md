# M0.9b — LightGCN Real-Data Pipeline Rationale

## Status

**LightGCN numerical core: IMPLEMENTED**

**LightGCN real-data pipeline: ENGINEERING VALIDATION CANDIDATE**

**LightGCN hyperparameters: NOT FROZEN**

**Overall M0 protocol: UNFROZEN**

This note records the engineering choices made when moving the tested M0.9a LightGCN core onto the real frozen KuaiRand-Pure training split.

The goal of M0.9b is not to tune LightGCN. It is to establish an end-to-end, deterministic, memory-bounded pipeline whose semantics remain consistent with the frozen training contract.

---

## 1. Choices inherited unchanged from BPR

LightGCN inherits the following RankLab training decisions rather than reopening them:

- standard-policy history only;
- Apr 9–16 training;
- Apr 17–21 validation;
- `is_click` as the primary training interaction;
- pair collapse by any-click;
- same-user exposed non-click pairs as eligible negatives;
- one negative per positive per epoch;
- uniform sampling with replacement;
- epoch-specific deterministic resampling from the model seed;
- macro NDCG@10 for validation;
- earliest epoch as the exact within-run validation tie-break.

These are training-contract decisions, not LightGCN hyperparameters.

---

## 2. LightGCN-specific graph semantics

The graph contains only positive click edges.

M0.9b additionally aligns the graph population with pairwise training eligibility:

> users with positive click pairs but zero eligible logged negatives are excluded from both the graph and pairwise LightGCN loss.

### Reason

BPR necessarily excludes these users from pairwise training.

Allowing LightGCN to retain them as graph-only context would give LightGCN access to an additional training population that BPR does not use. For RankLab's controlled comparison, population alignment is preferred over squeezing extra graph signal from otherwise ineligible users.

This choice should remain visible in the later BPR-vs-LightGCN rationale.

---

## 3. Propagation semantics

M0.9b preserves the M0.9a LightGCN definition:

- symmetric degree normalization;
- no learned feature transformation;
- no nonlinear activation;
- positive bipartite interaction graph;
- final representation is the arithmetic mean of layer 0 through layer `L`.

No architectural embellishments are introduced.

---

## 4. Memory-bounded optimization

The transparent M0.9a implementation computes a full-batch LightGCN+BPR gradient directly.

For real KuaiRand, materializing all per-triplet gradient arrays at once would use unnecessary memory.

M0.9b therefore accumulates the same full-batch gradient in chunks.

The procedure is:

1. compute propagated embeddings once at the start of an epoch;
2. iterate through sampled BPR triplets in deterministic chunks;
3. accumulate gradients with respect to the final propagated embeddings;
4. back-propagate the accumulated full-batch gradient through the LightGCN propagation operator;
5. apply one base-embedding update.

This is a memory-engineering change, not a deliberate change in the optimization objective.

The chunk size is therefore an engineering parameter rather than a model-selection parameter.

---

## 5. Why not introduce stochastic mini-batch LightGCN yet?

A conventional framework implementation could recompute graph propagation and update embeddings for each mini-batch.

RankLab does not need that complexity yet.

The immediate goal is to verify:

- real-data execution;
- deterministic checkpointing;
- reproducibility;
- learning capability;
- validation behavior.

The chunked full-batch implementation makes those semantics transparent and directly comparable to the already-tested M0.9a numerical core.

If later compute requirements force a different optimizer implementation, that change must be documented before the LightGCN hyperparameter sweep.

---

## 6. M0.9b acceptance criteria

Before this pipeline is considered engineering-valid, RankLab should verify:

1. all unit/integration tests pass;
2. the real KuaiRand frozen split reproduces the M0.7 pair/user counts;
3. a multi-epoch smoke run completes;
4. repeating the same run with the same seed produces the same checkpoint SHA256 and manifest;
5. a real-data diagnostic demonstrates that the LightGCN optimizer can reduce pairwise loss;
6. the observed validation score is interpreted in light of the shallow logged-candidate sets;
7. no Apr 22–May 8 labels are used.

Only after those checks should RankLab freeze a separate LightGCN hyperparameter-search protocol.
