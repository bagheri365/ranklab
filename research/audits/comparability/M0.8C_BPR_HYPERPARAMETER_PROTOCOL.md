# M0.8c — BPR Hyperparameter Search Protocol

## Status

**BPR hyperparameter search protocol: FROZEN BEFORE SWEEP**

**BPR selected configuration: NOT YET FROZEN**

**Overall M0 protocol: UNFROZEN**

This note freezes the search procedure that RankLab will use to choose the primary BPR configuration. It is intentionally written before the full sweep is executed.

The search may inspect only the frozen Apr 17–21 validation slice from the standard-policy history. It must not inspect Apr 22–May 8 standard-policy or randomized-exposure evaluation labels.

---

## 1. Goal

The purpose of this sweep is not to maximize BPR performance through an open-ended search.

The purpose is to choose one reasonable BPR configuration from a small, predeclared grid so that later RankLab comparisons reflect logging-regime and target instability rather than unconstrained model tuning.

---

## 2. Frozen data and training semantics

The sweep inherits the M0.7 training contract without modification:

```text
training source:
  standard-policy history only

training dates:
  2022-04-09 through 2022-04-16

validation dates:
  2022-04-17 through 2022-04-21

training interaction:
  is_click

positive pair:
  any-click collapsed user-video pair

eligible negative:
  exposed user-video pair with no click anywhere
  in the frozen training slice

negative sampling:
  one same-user logged negative per positive per epoch
  uniform with replacement
  resampled every epoch
  deterministic from the model seed

validation objective:
  macro NDCG@10

validation relevance:
  binary any-click
```

No part of M0.8c may alter those semantics.

---

## 3. Frozen hyperparameter grid

RankLab will evaluate the full Cartesian product:

| Hyperparameter | Values |
|---|---|
| Embedding dimension | `16`, `32`, `64` |
| Learning rate | `0.01`, `0.05`, `0.1` |
| L2 regularization | `1e-5`, `1e-4`, `1e-3` |

This produces:

```text
3 × 3 × 3 = 27 configurations
```

The following quantities are fixed rather than searched:

```text
maximum epochs: 30
batch size:      4096
init std:        0.01
tuning seed:     0
validation k:    10
negatives/positive/epoch: 1
```

---

## 4. Seed policy

Hyperparameter selection uses exactly one frozen seed:

```text
seed = 0
```

Using multiple seeds during the grid search would substantially increase compute and would allow the hyperparameter-selection stage to absorb stochastic variation into the search.

After one configuration is selected and frozen, RankLab may fit that selected configuration under the separate primary seed set required by the final study protocol.

The sweep must not choose a configuration by looking at future multi-seed M1 results.

---

## 5. Epoch-selection policy

Every configuration is trained for the full:

```text
30 epochs
```

There is **no early stopping** during the sweep.

For each configuration, the selected checkpoint is the epoch with the highest frozen-validation macro NDCG@10.

Exact within-configuration metric ties are broken by:

```text
earliest epoch
```

Training every configuration for the same maximum number of epochs removes patience and stopping-time choices from the hyperparameter search.

---

## 6. Configuration-selection rule

For each of the 27 configurations:

1. train using seed `0`;
2. evaluate Apr 17–21 macro NDCG@10 after every epoch;
3. retain that configuration's best epoch using the earliest-epoch tie-break;
4. compare the 27 configuration-level best NDCG@10 values.

The primary winning configuration is the one with the highest best validation NDCG@10.

### Exact tie-break between configurations

If two or more configurations have exactly equal best validation NDCG@10, choose deterministically by:

1. lower embedding dimension;
2. lower regularization;
3. lower learning rate;
4. earlier best epoch.

This tie-break is only for exact numerical equality. It is not a practical-significance rule.

---

## 7. No adaptive search

After the 27 configurations are evaluated:

- do not add a new learning rate because the best result lies at a grid boundary;
- do not add a new embedding size because a larger model appears promising;
- do not add a new regularization value;
- do not change the tuning seed;
- do not change the maximum epoch count;
- do not change validation dates;
- do not redefine candidate sets;
- do not inspect Apr 22–May 8 labels to revise the grid.

A follow-up search would require a new explicitly documented protocol revision before running it.

---

## 8. Required sweep record

The sweep artifact must preserve:

- source-data path and SHA256;
- frozen protocol SHA256;
- full grid definition;
- fixed training parameters;
- all per-epoch losses and validation NDCG@10 values;
- best epoch per configuration;
- best validation NDCG@10 per configuration;
- checkpoint SHA256 per configuration;
- deterministic winning configuration and selected checkpoint hash.

---

## 9. What this sweep may freeze

After the sweep completes and passes audit checks, RankLab may freeze:

- BPR embedding dimension;
- BPR learning rate;
- BPR regularization;
- selected epoch/checkpoint for the tuning seed.

It does not freeze LightGCN settings, final M1 seed aggregation, matched-support policy, uncertainty procedures, or regime/target contrast rules.

---

## 10. Interpretation

The result should be described as:

> the best configuration in the predeclared M0.8c BPR grid under the frozen Apr 17–21 standard-policy click-validation objective.

It should not be described as globally optimal BPR, optimal for `long_view`, or optimal under randomized exposure.
