# M0.19 — Evaluation Candidate and NDCG Semantics Freeze

## Status

**Candidate unit: FROZEN**

**Duplicate collapse: FROZEN**

**Target relevance collapse: FROZEN**

**Minimum candidate count: FROZEN**

**Primary metric and K: FROZEN**

**Less-than-K behavior: FROZEN**

**Zero-relevance handling: FROZEN**

**User aggregation: FROZEN**

**Test-time negative sampling: NONE**

**M1: STILL BLOCKED ON STATISTICAL/SELECTION FREEZE**

M0.19 freezes the final per-user ranking semantics after reviewing the
post-M0.18 label-only candidate audit.

## 1. Evidence from the post-eligibility audit

On the primary scoring population:

### Standard

- users: 22,882;
- unique candidate pairs: 263,719;
- candidate median: 9;
- candidate p90: 24;
- users with at least 2 candidates: 21,643;
- users with at least 10 candidates: 10,435.

### Randomized

- users: 22,882;
- unique candidate pairs: 923,746;
- candidate median: 20;
- candidate p90: 92;
- users with at least 2 candidates: 22,882;
- users with at least 10 candidates: 20,830.

A 10-candidate minimum would remove more than half of standard-policy users.
A one-candidate ranking is trivial and provides no meaningful ordering task.

Therefore RankLab freezes a minimum of 2 unique candidates.

## 2. Candidate unit

The ranking unit is one user.

Within a regime/support/target evaluation slice, candidates are unique
`(user_id, video_id)` pairs.

Repeated retained exposure rows for the same pair are collapsed before scoring.

No sampled test negatives are added.

Thus the candidate set is the user's retained logged item set after all frozen
support and scoring-eligibility restrictions.

## 3. Target-specific relevance collapse

For each retained user-video pair and target independently:

> relevance = 1 if any retained exposure row for that pair has target value 1;
> otherwise relevance = 0.

This rule is used for:

- `is_click`;
- `long_view`.

The targets remain separate. A positive click does not automatically define
`long_view`, and vice versa.

## 4. Minimum candidate-set size

A user must have at least:

`2`

unique eligible candidates.

Users with 0 or 1 candidate are excluded from ranking metrics and reported in
candidate-retention counts.

The threshold is target-independent.

## 5. Primary metric

Primary metric:

`macro NDCG@10`

Primary K:

`10`

NDCG is computed separately for each:

- model;
- model seed where applicable;
- logging regime;
- behavioral target;
- support analysis.

## 6. Less-than-K rule

If a user has:

`2 <= n_candidates < 10`

RankLab evaluates the full available ranked list of `n_candidates`.

It does not:

- pad with dummy items;
- sample extra negatives;
- duplicate candidates;
- discard the user merely because `n < 10`.

Mathematically this is ordinary DCG@10/IDCG@10 on a list shorter than K.

## 7. Zero-relevance users

If a user has no relevant candidate for the target, then IDCG is zero and NDCG
is undefined.

RankLab does **not** assign such a user NDCG=0.

Instead:

- exclude the user from that target's macro-NDCG denominator;
- report zero-relevance user counts and fractions separately.

Reason:

Zero-relevance rates differ substantially by regime and target even before
model scoring. Assigning NDCG=0 would mix ranking quality with outcome
prevalence/observability.

On primary post-eligibility support:

### Standard

- `is_click` zero-relevance users: 2,059 before the `>=2` candidate filter;
- `long_view` zero-relevance users: 3,636 before the `>=2` candidate filter.

### Randomized

- `is_click` zero-relevance users: 4,145;
- `long_view` zero-relevance users: 8,040.

Final reports must state the target-specific metric denominator after both the
candidate-count and zero-relevance rules are applied.

## 8. Gain and discount

Relevance is binary: `{0,1}`.

Gain:

`gain(rel) = rel`

Discount at one-indexed rank r:

`1 / log2(r + 1)`

For binary relevance, identity gain is numerically equivalent to the common
`2^rel - 1` gain, but identity gain is explicitly frozen for clarity.

## 9. Ranking order

The already-frozen M0.14 rule applies:

1. score descending;
2. `video_id` ascending for an exact score tie.

## 10. Aggregation

The aggregation unit is the user.

Primary per-run NDCG is the arithmetic mean across target-eligible users.

Every included user receives equal weight.

Exposure rows and candidate pairs are not used as aggregation weights.

## 11. No test-time negative sampling

RankLab does not sample evaluation negatives.

The logged eligible candidate set itself is ranked.

This prevents an extra stochastic evaluation layer and avoids making metric
values depend on an arbitrary negative-sampling ratio.

## 12. Frozen protocol fields

M0.19 freezes:

- `ranking_unit = user`;
- `candidate_rule = unique logged user-video pairs after frozen support and
  scoring eligibility`;
- `duplicate_rule = collapse pair with target-specific any-positive relevance`;
- `min_candidate_set_size = 2`;
- `<K rule = use all available candidates`;
- `test_negative_sampling = none`;
- `primary_metric = macro_ndcg`;
- `primary_k = 10`;
- `aggregation_unit = user`;
- `weighting_policy = equal_user_weight`;
- `zero_relevance_rule = exclude_from_target_macro_and_report`;
- `tie_breaking_rule = score_desc_then_video_id_asc`;
- `ndcg_gain = identity_binary`;
- `ndcg_discount = log2`;
- `relevance_scale = binary`.
