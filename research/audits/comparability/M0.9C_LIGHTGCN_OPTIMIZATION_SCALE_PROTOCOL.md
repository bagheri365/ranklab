# M0.9c — LightGCN Optimization-Scale Audit Protocol

## Status

**Audit protocol: FROZEN BEFORE EXECUTION**

**LightGCN hyperparameter-search protocol: NOT YET FROZEN**

**LightGCN final configuration: NOT SELECTED**

**Overall M0 protocol: UNFROZEN**

This audit exists because the real-data M0.9b smoke run and learning diagnostic showed that LightGCN's effective optimization scale differs materially from BPR's.

It is intentionally narrower than a hyperparameter sweep.

Its purpose is to choose a defensible **learning-rate range** for the later LightGCN model-selection search.

It must not be used to declare a final LightGCN winner.

---

## 1. Why this audit is needed

The initial M0.9b real-data smoke run used:

- embedding dimension 32;
- one LightGCN propagation layer;
- learning rate 0.1;
- regularization `1e-4`;
- five-digit-scale gradient chunking;
- seed 0.

Across the three smoke epochs, validation macro NDCG@10 did not change.

A separate 500-user learning-capability diagnostic used a much stronger learning rate of 5.0 for 20 epochs and reduced fixed-triplet BPR loss, but only modestly.

Together these observations show that blindly copying BPR's learning-rate grid would not be justified.

The LightGCN optimizer combines:

- full-graph propagation;
- layer averaging;
- a full-batch parameter update after accumulating all sampled triplet gradients.

That produces a different effective update scale from the mini-batch BPR implementation.

Therefore RankLab performs one predeclared optimization-scale audit before freezing the actual LightGCN hyperparameter grid.

---

## 2. Variable under audit

Only **learning rate** varies.

The predeclared values are:

- `0.1`
- `0.5`
- `1.0`
- `2.0`
- `5.0`

No additional learning rates may be added after inspecting the audit results.

---

## 3. Fixed settings

For every audit run:

- embedding dimension: `32`
- LightGCN propagation layers: `1`
- regularization: `1e-4`
- gradient chunk size: `8192`
- epochs: `5`
- initialization std: `0.01`
- seed: `0`
- validation metric: macro NDCG@10
- training/validation dates: frozen M0 contract
- negative sampling: frozen same-user logged-negative rule
- graph population: pairwise-eligible positive users only

These settings are held fixed because this is not yet a multidimensional model-selection exercise.

---

## 4. Recorded quantities

For every learning rate, record:

- epoch-by-epoch training loss;
- epoch-by-epoch validation macro NDCG@10;
- best validation epoch;
- best validation macro NDCG@10;
- checkpoint SHA256;
- loss change from epoch 1 to epoch 5;
- whether validation ranking changes across the five epochs.

---

## 5. Interpretation rules

The audit will be interpreted qualitatively to define the later LR search range.

Useful signals include:

- learning rates whose losses visibly move in the intended direction;
- learning rates that begin to change validation rankings;
- learning rates that show obvious instability or explosive loss;
- ranges where behavior remains effectively frozen.

This audit does **not** predeclare a rule such as "pick the LR with the highest validation score" because doing so would turn it into an undeclared model-selection sweep.

Instead, after all five values are observed, RankLab will document a bounded LR range for the formal LightGCN sweep.

The formal sweep configuration grid and tie-breaking rules must then be committed **before** that sweep is run.

---

## 6. Leakage guardrails

The audit may use only:

- Apr 9–16 standard-policy training data;
- Apr 17–21 standard-policy validation data.

It must not inspect:

- Apr 22–May 8 standard-policy evaluation labels;
- randomized-policy evaluation labels.

---

## 7. Rationale-trail role

This audit is an important asymmetry between the BPR and LightGCN development paths.

BPR's predeclared search grid could be frozen directly after its real-data engineering checks.

LightGCN required an additional model-specific optimization-scale audit because its full-graph gradient produced much smaller visible movement under the initial smoke settings.

That difference should be retained in the later BPR-vs-LightGCN methodology synthesis rather than smoothed over.
